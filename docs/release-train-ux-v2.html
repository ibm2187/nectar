Release Train UX v2

Zero-setup: milestones auto-compute, pipeline just shows up, configuration is inline.

Core shift: Release trains are automatic, not opt-in. JIRA tells us the version (→ type) and release date (→ ship date). Nectar attaches milestones on every release with no user action. The pipeline is always visible. Editing is contextual — click the thing you want to change.

Before vs After

Before — Opt-in setup

  • User sees big "Configure Release Train" card
  • Forced to pick type + ship date before anything shows
  • Setup is a prerequisite, not a byproduct
  • Manual step for every single release
  • Defaults buried behind a button click

After — Auto-configured

  • JIRA sync auto-attaches milestones on create
  • Pipeline always renders when data allows
  • Release type + ship date inline-editable in header
  • Click any gate to adjust, complete, or override
  • Configuration only appears when needed

How it works

1
JIRA sync runs. Detects version "4.2.7-lumen" and releaseDate "2026-04-22".
2
Nectar infers release type. Patch > 0 → point release. Patch = 0 → monthly. Can't determine? leave blank.
3
Milestones auto-compute. From the template for that type, T-minus dates are calculated from ship date.
4
Release detail page renders the pipeline. No setup card. No button. Just the gate bar.
5
User edits inline. Click the ship date to change it. Click the type to change it. Click a gate to override or complete.

What we remove

  • ✗ The full-width "Configure Release Train" setup card
  • ✗ The separate /configure step and pre-setup state
  • ✗ The large "Set up as Point Release shipping..." prompt
  • ✗ Button-driven flows for edits (type, ship date)

What stays

  • ✓ Gate pipeline with same states (met / active / pending / missed / skipped)
  • ✓ Click gate → detail panel with Mark Complete / Skip / Override Date
  • ✓ Per-milestone override preserves across ship date changes
  • ✓ Scorecard view after ship (gate hit rate, missed gates)
  • ✓ Template editor in /config (unchanged)
