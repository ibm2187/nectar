1. What We're Building

Four capabilities, layered so each is independently useful:

CapabilityWhat It DoesWho Uses It
Configurable TemplatesDefine T-minus milestones per release type. Editable in Nectar settings — no code deploy needed.CTO, PM
Gate PipelineVisual gate-by-gate status on every release. Auto-checks + manual sign-offs. Blocks progression when criteria aren't met.PM, Dev Lead, QA Lead
Process ReportingRelease scorecards, cross-release trends, milestone compliance, scope creep tracking.CTO, PM
Alerts & EnforcementSlack alerts on missed gates, freeze violations, SLA breaches. RCA countdown tracking.Everyone
Design principle: The process lives inside the release workflow, not in a separate doc. Every gate shows its rules when you click it. The process page is the reference — the gate pipeline is the daily driver.

4. Implementation Phases

7 phases, each independently shippable. Total estimate: ~16-18 days.

~2 daysPhase 1: Configurable Templates

  • release_templates table + migration
  • Seed default templates (monthly, point, hotfix) from the RFC
  • T-minus date computation engine: computeMilestones(shipDate, template) — skips weekends
  • API: GET/PUT /settings/release-templates
  • Template versioning (auto-increment on save)

Tests: Date computation with weekends, holidays, edge cases (ship date on Monday). Template CRUD. Version increment.

~2 daysPhase 2: Release Milestones

  • Add releaseType, shipDate, milestones, templateVersion columns to releases
  • On create: snapshot template → compute concrete dates → store as milestones JSON
  • On ship date change: recompute all non-overridden dates
  • Manual override: PATCH /releases/:version/milestones/:key { overrideDate }
  • Manual sign-off: POST /releases/:version/milestones/:key/complete
  • Skip milestone: POST /releases/:version/milestones/:key/skip
  • Update CreateReleaseDialog: add release type picker + ship date + milestone preview

Tests: Milestone creation from template. Override priority (manual > computed). Recompute on ship date change preserves overrides. Skip behavior. Status transitions.

~3 daysPhase 3: Gate Pipeline UI

  • GatePipeline component — horizontal pipeline replacing existing timeline bar
  • Gate nodes: color-coded by status (green/orange/red/grey)
  • Click → popover with: description, owner, due date, blocking items, miss consequence
  • Action buttons in popover: Override Date, Mark Complete, Skip
  • Auto-check integration: connect gate checkers to truth engine data
  • Template settings page: milestone editor UI on /config

Tests: Component rendering for each status. Popover actions. Auto-check function mapping. Settings CRUD UI.

~2 daysPhase 4: Auto-Check Functions

  • Gate checker registry: map autoCheck keys to functions
  • all-tickets-have-target-version — query JIRA tickets for this version
  • all-prs-merged — truth engine: all planned tickets have commits on master
  • branch-exists — check release.branch exists, release.cutAt is set
  • truth-all-certified — truth engine: 100% tickets = certified health
  • migrations-approved — all migration entries have dbaApproved = true
  • time-based — current date >= milestone date
  • state-is-done — release.state = 'done'
  • API: GET /releases/:version/gates — returns all milestones with live auto-check results

Tests: Each checker function independently. Gate aggregation. Partial completion states.

~3 daysPhase 5: Reporting

  • release_scorecards table + auto-compute when release state → done
  • Scorecard computation: gate hit rate, on-time ship, scope changes, SLA compliance, cycle time
  • API: GET /releases/:version/scorecard
  • API: GET /reports/process-health?releases=10 — cross-release trends
  • API: GET /reports/upcoming-milestones — all pending milestones across active releases
  • Scorecard component on ReleaseDetail (post-ship)
  • /reports/process-health page with trend table + upcoming milestones

Tests: Scorecard computation accuracy. Trend aggregation. Edge cases (release with no milestones, skipped gates). Upcoming milestones ordering.

~2 daysPhase 6: Alerts & Enforcement

  • Milestone overdue detector: runs on schedule, checks pending milestones past due date
  • Scope creep detector: ticket added to version after scope-lock milestone is met
  • Freeze violation detector: cherry-pick PR detected after CP freeze milestone is met
  • RCA countdown: hotfix shipped → 48h timer. Alert if not filed.
  • Slack integration: POST /releases/:version/notify extended for milestone alerts
  • Audit trail: all milestone status changes logged in existing audit table

Tests: Overdue detection timing. Scope creep with edge cases (ticket moved before vs. after lock). Freeze violation with CHERRY_PICK label. Slack payload formatting.

~2 daysPhase 7: Process Page

  • /process route — living version of the RFC
  • Content pulled from templates (so it updates when templates change)
  • Sections: Three Tracks, Release Lead, T-Minus Runway (per type), Hard Rules, Escalation
  • Each milestone links to its template definition
  • Links to process health reports for live enforcement examples

Tests: Page renders. Template changes reflected. Links to live data resolve.

Critical Test Scenarios

  • Date math: Ship date = Wednesday. T-25 computed correctly skipping weekends. Ship date on a Monday (should adjust?). T-minus = 0 edge case.
  • Override priority: Manual override takes precedence. Clear override snaps back to computed. Ship date change recomputes non-overridden only.
  • Template versioning: Template v2 doesn't affect releases created with v1. New releases get v2.
  • Gate auto-checks: truth-all-certified with 100% vs 99% vs 0%. branch-exists when branch is null. time-based across timezone boundaries.
  • Scorecard accuracy: Release with all gates met = 100%. Release with 1 missed = correct %. Scope creep count matches actual ticket additions after scope-lock date.
  • Concurrency: Two users override the same milestone. Scorecard computation during active release.
